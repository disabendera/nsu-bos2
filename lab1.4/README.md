# Лабораторная работа 1.4

## a. Отмена потока с точками отмены (`thread_a.c`)

**Практика:**

Рабочий поток выполняет бесконечный цикл с `printf()` и `usleep()`.
Главный поток через некоторое время вызывает:

``` c
pthread_cancel(tid);
```

а затем:

``` c
pthread_join(tid, NULL);
```

`pthread_cancel()` отправляет потоку запрос на отмену, а
`pthread_join()` ждёт его фактического завершения.

**Теория:**

По умолчанию отмена потока разрешена (`PTHREAD_CANCEL_ENABLE`), а её тип
--- отложенный (`PTHREAD_CANCEL_DEFERRED`).

При отложенной отмене `pthread_cancel()` не обязан завершать поток
мгновенно. Запрос на отмену обрабатывается, когда поток достигает
**точки отмены (cancellation point)**.

В нашей программе рабочий поток регулярно вызывает функции, при
выполнении которых запрос на отмену может быть обработан, поэтому после
`pthread_cancel()` поток завершается, а `pthread_join()` успешно
возвращается.

Важно различать: - `pthread_cancel()` --- отправляет запрос на отмену; -
`pthread_join()` --- ждёт, пока поток действительно завершится.

## b. Отмена вычислительного потока (`thread_b.c`)

**Практика:**

Рабочий поток выполняет бесконечный вычислительный цикл:

``` c
while (1) {
    counter++;
}
```

Внутри цикла нет явной точки отмены. Поэтому при стандартной отложенной
отмене запрос от `pthread_cancel()` может остаться необработанным, а
главный поток будет продолжать ждать внутри `pthread_join()`.

**Теория:**

Обычные арифметические операции вроде `counter++` не являются точками
отмены. Чтобы вычислительный поток мог регулярно реагировать на запрос
отмены, в цикл можно добавить:

``` c
pthread_testcancel();
```

`pthread_testcancel()` создаёт явную точку отмены. Если запрос на отмену
уже есть, поток завершится; если запроса нет, выполнение продолжится.

Также существует тип отмены `PTHREAD_CANCEL_ASYNCHRONOUS`. При
асинхронной отмене поток может быть отменён без ожидания обычной точки
отмены. Такой режим опасен, потому что поток может завершиться в
неудобный момент: например, удерживая mutex или изменив только часть
общих данных. Поэтому обычно предпочтительнее отложенная отмена с
контролируемыми точками отмены.

Полезно различать две настройки: - `pthread_setcancelstate()` ---
разрешена ли отмена (`ENABLE` / `DISABLE`); - `pthread_setcanceltype()`
--- как выполняется разрешённая отмена (`DEFERRED` / `ASYNCHRONOUS`).

По умолчанию используется `ENABLE + DEFERRED`.

## c. Обработчики очистки (`thread_c.c`)

**Практика:**

Рабочий поток выделяет память через `malloc()`:

``` c
char *msg = malloc(20);
```

После этого регистрируется обработчик очистки:

``` c
pthread_cleanup_push(cleanup_handler, msg);
```

Обработчик освобождает выделенную память:

``` c
void cleanup_handler(void *arg) {
    char *msg = (char *)arg;
    free(msg);
}
```

Если поток отменяется через `pthread_cancel()`, зарегистрированный
обработчик очистки выполняется и память не остаётся потерянной.

**Теория:**

Cleanup handler нужен для освобождения ресурсов, которыми владеет поток.
Это может быть динамическая память, mutex, файловый дескриптор и другие
ресурсы.

Можно зарегистрировать несколько обработчиков. Они выполняются в
обратном порядке регистрации --- последний добавленный обработчик
выполняется первым (LIFO).

`pthread_cleanup_pop()` снимает последний зарегистрированный обработчик:

``` c
pthread_cleanup_pop(1);
```

--- снять обработчик и выполнить его;

``` c
pthread_cleanup_pop(0);
```

--- снять обработчик, но не выполнять его.

Зарегистрированные cleanup handlers выполняются при отмене потока и при
завершении через `pthread_exit()`. При нормальном пути выполнения
программы очистку можно явно выполнить через `pthread_cleanup_pop(1)`.

`pthread_cleanup_push()` и `pthread_cleanup_pop()` являются макросами и
должны использоваться согласованной парой в одной области кода.

------------------------------------------------------------------------

## Cleanup и `pthread_join()` --- не одно и то же

Обработчик очистки освобождает ресурсы, которыми управляла наша
программа. Например, `free(msg)` освобождает память, выделенную через
`malloc()`.

`pthread_join()` решает другую задачу: он ждёт завершения
joinable-потока, позволяет получить его результат и завершить работу с
ресурсами самого pthread.

Поэтому после отмены joinable-потока главный поток всё равно вызывает:

``` c
pthread_join(tid, NULL);
```

------------------------------------------------------------------------

## Главное по лабораторной

`pthread_cancel()` отправляет запрос на отмену потока. По умолчанию
используется отложенная отмена, поэтому запрос обрабатывается в точке
отмены.

В вычислительном цикле без подходящих точек отмены можно явно вызвать
`pthread_testcancel()`.

Cleanup handlers нужны для того, чтобы при отмене потока корректно
освободить захваченные им ресурсы. Они выполняются в обратном порядке
регистрации.
