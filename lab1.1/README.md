# Лабораторная работа 1.1

## a. Создание потоков посредством POSIX API (`thread.c`)
**Практика:**
Создание потока происходит через: `pthread_create(&tid, NULL, mythread, NULL)` (1. ID потока, 2. атрибуты, 3. стартовая функция, 4. аргументы). Функция `mythread` распечатывает PID, PPID и TID. Без `pthread_join` главный поток может завершиться раньше, уничтожив дочерние.

**Теория:**
У всех потоков одного процесса **общий PID, но у каждого свой TID**. 
*Поведение при завершении `main`:* Если `main` завершается через `return 0;` или доходит до конца, библиотека `glibc` вызывает системный вызов `exit_group()`, который **мгновенно убивает все потоки процесса**, не давая им освободить ресурсы. Единственный нормальный POSIX-вариант завершить только главный поток, оставив остальные работать в фоне (без `pthread_join()`) — вызвать `pthread_exit(NULL);` в `main`.

## b. Создание 5 потоков (`thread_5.c`)
Главный поток в цикле создает 5 дочерних и затем последовательно вызывает `pthread_join()` для каждого

**Теория:** Внутри `pthread_join()` используется гибридная блокировка. Если целевой поток еще работает, вызывающий поток засыпает на механизме `futex` (Fast Userspace Mutex), не тратя процессорное время впустую (`FUTEX_WAIT`).

## c. Идентификаторы потоков (`thread_c.c`)
**Практика:** Для идентификации используются `gettid` (ID потока в Linux) и `pthread_self` (ID в формате POSIX).

**Теория:**
1. **`gettid()`**: Возвращает ядерный TID (LWP - Light Weight Process). Ядро использует его для планирования процессорного времени (диспетчеризации).
2. **`pthread_self()`**: Стандарт POSIX определяет `pthread_t` как непрозрачный тип. В реализации `glibc`/NPTL на Linux `pthread_self()` возвращает просто **виртуальный адрес структуры `struct pthread` (TCB - Thread Control Block)**.
3. **Почему `pthread_equal`?** Так как `pthread_t` может быть структурой на других ОС, оператор `==` неприменим. Нужно использовать `pthread_equal()` для переносимости кода.

*Где физически лежит TCB?* 
Когда библиотека `glibc` выделяет память под стек нового потока через `mmap()`, она размещает структуру TCB (`struct pthread`) на самом верху этого выделенного региона памяти. Стек будет расти вниз, а TCB безопасно лежит на самом верху.

*Что внутри TCB и как поток его находит?*
В TCB хранится ядерный TID, флаг joinable/detached, локальные данные (TSD) и копия `errno` для этого потока. При вызове `clone3()` флаг `CLONE_SETTLS` настраивает аппаратный регистр (например, `%fs` на x86-64) так, чтобы он указывал прямо на адрес этого TCB в памяти. Поэтому вызов `pthread_self()` отрабатывает мгновенно — он просто читает адрес из этого регистра без системных вызовов в ядро.

## d. Области видимости и адреса переменных (`thread_d.c`)
**Практика:**
1. *Локальная переменная*: хранится в стеке потока, изменения не видны другим.
2. *Локальная статическая*: память выделяется в статической области данных процесса, все потоки видят один и тот же объект.
3. *Локальная константная*: локальна по области видимости, хранится в стеке потока.
4. *Глобальная переменная*: в общей области памяти, все видят один объект.

**Теория:**
Все потоки делят одно виртуальное и физическое адресное пространство (VAM и PhAM) благодаря флагу `CLONE_VM`, передаваемому в ядро. Поэтому сегменты инициализированных (`.data`) и неинициализированных (`.bss`) данных (где лежат статические и глобальные переменные) общие. Стеки же выделяются раздельно (через `mmap`), поэтому локальные переменные изолированы. Мутация общих переменных требует использования примитивов синхронизации (мьютексы/futex) во избежание состояния гонки.

## e. Изучение /proc/<pid>/maps и стеков (`thread_e.c`)
**Практика:**
В `/proc/<pid>/task` были найдены потоки 68478, 68479, 68480, 68481, 68482, 68483. У них общий PID (68478), но разные TID. 
В `/proc/68478/maps` найдена область `7ffe290b8000-7ffe290d9000 rw-p [stack]` — это стек основного потока. 
Стеки других потоков наблюдаются через `/proc/<pid>/task/<tid>/maps`. В `/proc/<pid>/task/<tid>/stack` зафиксированы вызовы ядра: `futex_wait_queue_me`, `futex_wait`, `do_futex`.

**Теория:**
Вызовы `futex_wait` в стеке означают, что главный поток заблокирован внутри `pthread_join()`, ожидая сигнала `FUTEX_WAKE` от завершающегося дочернего потока. 
Стеки для дочерних потоков аллоцируются библиотекой `glibc` через `mmap()`. Чтобы защитить память от переполнения стека (например, при бесконечной рекурсии), `glibc` использует системный вызов `mprotect(addr, 4096, PROT_NONE)` на самую нижнюю страницу этого региона. Это создает **Guard Page** (минную страницу). Обращение к ней мгновенно вызывает `SIGSEGV`, защищая память соседних потоков.

## f. Системные вызовы при создании потоков (strace)
**Практика:**
Создание потока (и `pthread_create`) строится на системном вызове `clone()` / `clone3()`. Сигнатура `clone` принимает указатель на функцию, вершину нового стека, флаги и аргументы. В трассировке также замечены `set_robust_list`, `futex`, `mmap`, `mprotect`.

**Теория флагов `clone3()`:**
Вызов `clone()` отличается от `fork()` именно набором флагов, которые превращают "клон" в поток:
*   `CLONE_VM` — единое адресное пространство с создателем.
*   `CLONE_FS` и `CLONE_FILES` — общие атрибуты файловой системы (cwd, umask) и таблица открытых дескрипторов.
*   `CLONE_SIGHAND` — общая таблица обработчиков сигналов.
*   `CLONE_THREAD` — ключевой флаг. Помещает новый поток в ту же thread group, обеспечивая всем потокам одинаковый PID (результат `getpid()`).
*   `CLONE_SETTLS` — настраивает регистр аппаратного потока на адрес TCB (для `pthread_self`).
*   `CLONE_PARENT_SETTID` — ядро синхронно записывает ядерный TID в выделенную память создателя (в структуру TCB).
*   `CLONE_CHILD_CLEARTID` — при завершении потока ядро автоматически обнуляет ячейку с TID и делает `FUTEX_WAKE`, чтобы разбудить тех, кто вызвал `pthread_join()`.
*   `set_robust_list` — регистрирует список надежных мьютексов (чтобы ядро могло освободить их, если поток умрет, не отпустив блокировку).
