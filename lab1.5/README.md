# Лабораторная работа 1.5

## a. Маршрутизация сигналов в потоках (`thread_a.c`)
**Практика:**
Создаются три потока с различным поведением относительно сигналов. Главный поток направленно отправляет сигналы через системный вызов `pthread_kill()`.
1. **Поток 1** через `pthread_sigmask(SIG_BLOCK, ...)` заполняет свою маску всеми сигналами (через `sigfillset`) и игнорирует всё.
2. **Поток 2** разблокирует `SIGINT` и перехватывает его через классический асинхронный обработчик (`sigaction`). Внутри обработчика используется `write()` вместо `printf()`, так как `printf` не является *async-signal-safe* и может вызвать deadlock.
3. **Поток 3** синхронно перехватывает `SIGQUIT` с помощью функции `sigwait()`.

**Теория:**
Архитектура Linux разделяет атрибуты сигналов на процесс-зависимые (глобальные) и потоко-зависимые (локальные):
*   **Глобально (на уровне всего процесса):** Диспозиции сигналов (какая функция вызовется при получении сигнала). Если вызвать `sigaction()` для `SIGINT`, это правило устанавливается для всего приложения (для всех TCB в рамках TGID).
*   **Локально (на уровне потока):** Маска блокировок (`sigmask`). У каждого потока (в его TCB) есть личная маска заблокированных сигналов. 
Поэтому, если сигнал направлен всему процессу (например, `kill PID` из консоли), ядро Linux пройдется по списку потоков и доставит сигнал **одному произвольному потоку**, в маске которого этот сигнал не заблокирован. Если мы используем `pthread_kill(tid)`, сигнал доставляется адресно конкретному потоку.

## b. Ответ на вопрос: "Можно ли установить обработчики сигнала для каждого потока?"
**Ответ:** НЕТ. Назначить *разные* функции-обработчики одного и того же сигнала для разных потоков в стандарте POSIX **невозможно**. 

**Объяснение механики:**
Массив указателей на функции-обработчики сигналов (таблица `sigaction`) является общей структурой данных ядра, которая копируется с флагом `CLONE_SIGHAND` при вызове `clone()`. Все потоки делят одну и ту же таблицу. Если Поток 1 установит `handler_A` для `SIGINT`, а Поток 2 попытается установить `handler_B` для `SIGINT`, то второй вызов просто перезапишет значение для всего процесса целиком.

**Как решается задача маршрутизации (Паттерн):**
Поскольку таблица обработчиков общая, управление доставкой осуществляется через **Маски Сигналов (`pthread_sigmask`)**:
1. Главный поток в самом начале блокирует целевой сигнал. Все дочерние потоки наследуют эту заблокированную маску.
2. Создается *один конкретный поток*, в котором этот сигнал разблокируется (или слушается через `sigwait`).
В итоге, когда процессу прилетает сигнал, ядро видит, что у 99% потоков он заблокирован, и гарантированно доставляет его в тот самый единственный выделенный поток.

## Правильный паттерн работы с сигналами (POSIX Recommended)
Асинхронные обработчики сигналов (`sigaction`) — это устаревшее и крайне опасное наследие в многопоточных программах. Поток может быть прерван сигналом в момент, когда он заблокировал мьютекс или обновлял память. Если обработчик попытается взять этот же мьютекс, произойдет самоблокировка (deadlock).

Поэтому стандарт POSIX настоятельно рекомендует **Синхронную обработку сигналов** (как это реализовано в Потоке 3):
1. Блокируем все асинхронные сигналы в главном потоке до старта программы.
2. Создаем один выделенный поток («Ловец сигналов»).
3. В этом потоке запускаем бесконечный цикл с вызовом `sigwait()` (или `sigtimedwait()`/`sigwaitinfo()`).
В этом случае поток просто спит. При поступлении сигнала ядро будит поток, и он обрабатывает сигнал **синхронно**, как обычный линейный код. В таком потоке безопасно использовать `printf()`, `malloc()`, блокировать мьютексы и общаться с другими потоками.
