# Шпаргалка: Процессы, Системные потоки и Пользовательские потоки

## 1. Базовые концепции и Память
*   **Процесс:** Изолированная программа, выполняющаяся в ОС. В Linux описывается структурой `task_struct` + структурой управления памятью `mm_struct`.
*   **Системный поток (Kernel Thread):** Легковесная единица выполнения внутри процесса. Создается системным вызовом `clone()` с флагами разделения памяти (`CLONE_VM`).
*   **Адресное пространство:** Каждому процессу ОС выдает иллюзию монопольного владения памятью (виртуальная память). ОС транслирует виртуальные адреса в физические через **Таблицы страниц (Page Tables)**.
    *   **У процессов:** Разные таблицы страниц. Память строго изолирована.
    *   **У потоков одного процесса:** Общие таблицы страниц, общая куча (heap), код и глобальные переменные. **Стек и регистры процессора — уникальные** для каждого потока.

## 2. Сравнение: Потоки против Процессов

| Характеристика | Процессы | Потоки (Threads) |
| :--- | :--- | :--- |
| **Изоляция и Безопасность** | **+** Максимальная. Ошибка в одном не роняет другие. | **-** Отсутствует. Segfault в одном потоке убивает весь процесс. |
| **Обмен данными (IPC)** | **-** Медленный (пайпы, сокеты, очереди сообщений ОС). | **+** Мгновенный (через общие переменные в памяти). |
| **Создание (`fork` vs `clone`)** | **-** Медленное (копирование таблиц страниц, создание структур). | **+** Быстрое (переиспользование `mm_struct` родителя). |
| **Синхронизация** | **+** Проще (нет общей памяти по умолчанию). | **-** Сложная (мьютексы, семафоры, риск Deadlock и Race Condition). |

## 3. Что происходит при переключении контекста (Context Switch)
Это ответ на вопрос, **почему потоки быстрее процессов**.

Переключением управляет планировщик ОС (например, CFS в Linux). Процедура состоит из двух этапов:
1.  **Сохранение/загрузка регистров (`switch_to`):** Сохранение состояния процессора (Instruction Pointer, Stack Pointer и др.). Выполняется всегда.
2.  **Переключение памяти (`switch_mm`):** Замена таблиц страниц.

**При переключении ПРОЦЕССОВ:**
*   ОС видит разные `mm_struct`.
*   Ядро перезаписывает аппаратный **регистр CR3** (в x86), указывая новый корень таблиц страниц.
*   **Следствие (Штраф):** Перезапись CR3 аппаратно сбрасывает **кэш TLB** (Translation Lookaside Buffer — кэш трансляции адресов). Процессор начинает тратить сотни тактов на Page Walks (вычисление физических адресов), пока TLB не прогреется заново. Происходит сильная просадка производительности (Cache Miss).

**При переключении ПОТОКОВ:**
*   ОС видит, что `mm_struct` совпадает.
*   Перезапись регистра CR3 **пропускается**.
*   **Следствие (Победа):** Кэш TLB не сбрасывается. Поток продолжает работать на «горячем» кэше памяти мгновенно.

## 4. Зачем придумали пользовательские потоки (Green Threads, Goroutines)
**Проблема системных потоков:**
Хотя системные потоки быстрее процессов, ими всё равно управляет ядро (ОС). 
*   Любое переключение контекста, создание потока или блокировка (на мьютексе/сетевом сокете) требует перехода процессора из **User Mode (Ring 3)** в **Kernel Mode (Ring 0)** и обратно. Это съедает тысячи тактов.
*   Каждый системный поток требует большой стек в памяти (2–8 МБ). Создать 100 000 системных потоков для веб-сервера невозможно — кончится RAM.

**Решение — Пользовательские потоки:**
Потоки, которыми управляет не ОС, а *рантайм языка программирования* (Go, Erlang, Rust/Tokio) в пространстве пользователя (User Space).

*   **Как это работает:** Рантайм создает несколько системных потоков (по числу ядер CPU). Внутри них он жонглирует десятками тысяч пользовательских потоков.
*   **Преимущества:**
    *   Стек динамический и крошечный (начинается с ~2 КБ).
    *   Переключение контекста происходит **без обращения к ядру ОС** (остается в Ring 3). Рантайм просто перекидывает указатель стека и пару регистров в памяти. Это занимает ~10-20 наносекунд (в 100 раз быстрее системного переключения).
*   **Работа с I/O (Критический момент):**
    Чтобы блокировка одного пользовательского потока при чтении из сети не усыпила системный поток ОС целиком, используется неблокирующий ввод-вывод (через **`epoll`** или **`io_uring`**). Рантайм паркует ожидающий поток, регистрирует сокет в `epoll` и мгновенно переключает CPU на выполнение другого пользовательского потока.
